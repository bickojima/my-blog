## 判断

既存PR #171を継承。npm audit fixで互換範囲内の依存を更新し、serveが固定するcompression 1.8.1のみoverrideで修正版1.8.2以降へ上げる。serveはPlaywright webServerと既存エビデンスで使用中のため削除しない。npmが提案するserve 10へのダウングレードは採用しない。sharpの同梱libvipsも1.3.4へ更新する。

## 不具合と5 Whys

1. 脆弱性が残った理由: lockfileが修正前の版を保持していた。
2. なぜ自然に更新されないか: npm ciはlockfileを再現する。
3. compressionだけ残る理由: serveが1.8.1へ固定している。
4. なぜ通常のaudit fixで直らないか: 親の宣言を超えた解決が必要。
5. なぜ依存削除で解消しないか: serveはE2Eで実利用される。

最小変更としてパッチ互換のoverrideを採用。再発防止はaudit 0件確認と、serve経由の全E2E・画像処理を含むビルドで検証する。

## 検証

npm ci --ignore-scripts、npm audit --package-lock-only 0件、Vitest 765件PASS、20ページのビルド成功。全E2E・包括検証・自己レビュー・staging/本番の結果は後段に追記する。


## 検証環境の切り分け

最初のE2EはPlaywright 1.58.2用のheadless browser未配置で失敗。Node26.12.1で公式インストーラを実行すると、Chrome ZIPダウンロード後の展開が途中で停止した。小さいZIPの最小再現はNode26/24とも成功したが、実際の同じChrome配布ZIPを同じPlaywright extract関数へ渡すとNode24.22.1では展開成功した。Node26側停止の内部根本原因までは断定しない。専用インストーラを通常のSIGINTで中断し（共有サービスは対象外）、同梱Node24で公式CLIを再実行するとブラウザ2種の準備が完了した。以後のブラウザ検証には同じNode24を使用し、対象アプリ・共有ランタイム・テストケースは変更しない。

並行セッションがPR #171をstagingへマージしたため、元ブランチを再pushしない。補足成果物は新規ブランチでstagingへ追加し、staging→mainのリリース経路を維持する。並行セッション終了は所有者から確認済み。
